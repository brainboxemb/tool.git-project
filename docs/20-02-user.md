# User manual

Use `tool.git-project` when a repository needs shared, domain-neutral repository
mechanics without embedding Java, SCAD or another domain build system.

## Typical consumers

Typical consumers are:

- product/project repositories;
- domain tools such as `tool.scad-project` and `tool.java-project`;
- reusable libraries that need the same repository bootstrap/update behavior;
- reusable CI workflows that need generic generated-output or release mechanics.

## Bootstrap dependency

The consumer pins `tool.git-project` directly as the committed gitlink:

```text
tools/tool.git-project
```

The bootstrap engine is intentionally not self-managed through `project.yml`.

Current root launcher families are:

```text
bootstrap.ps1
bootstrap.sh
update.ps1
update.sh
```

They are managed copies from the exact pinned tool revision. See
[30-11 — Managed consumer launchers](30-11-managed-consumer-launchers.md).

## Repository configuration

Generic dependency/profile intent lives in `project.yml`.

Start with [30-10 — Project format](30-10-project-format.md).

Domain-specific settings remain in profile files such as
`project.scad.yml` or `project.java.yml` and are opaque to this generic tool.

## Normal operations

Direct tool checkout:

```bash
./git-project.sh validate
./git-project.sh bootstrap
./git-project.sh status
./git-project.sh update
```

Consumer root:

```bash
./bootstrap.sh
./update.sh status
./update.sh
```

PowerShell provides equivalent `.ps1` entrypoints.

After an update, review the parent repository's gitlink changes before commit.

## Choosing versions

Use a released semantic tag for reusable workflows/actions. The consumer's
committed `tools/tool.git-project` gitlink records the exact bootstrap revision.

A root launcher never silently advances that parent gitlink.
